# FLAME `.pkl` vs `.obj`: Relationship and `load_obj()` Explained

This document explains the two FLAME model files, what `load_obj()` returns, how UV mapping works, and why both files are needed.

---

## 1. The Two FLAME Model Files

FLAME uses **two** separate files to represent the head model:

| File | Path | Format | Purpose |
|------|------|--------|---------|
| `.pkl` | `generic_model.pkl` | Python pickle (Chumpy/NumPy) | Statistical deformation model (blend shapes, skinning, joints) |
| `.obj` | `head_template_mesh.obj` | Wavefront OBJ | Template mesh geometry **with UV mapping** |

### Why two files?

The `.pkl` comes from the original FLAME release (MPI). It contains everything needed to **deform** the mesh — but it stores **no UV/texture information**. The `.obj` was created separately (exported from Blender, as the file header shows) to provide **UV coordinates** for texture mapping. Both share the **same topology** (same vertex count, same face connectivity).

---

## 2. What's Inside the `.obj` File

The file `head_template_mesh.obj` contains:

```
# Blender v2.80 (sub 75) OBJ File: 'flame_new_uv_map.blend'
v 0.061998 1.493503 -0.027215      ← 3D vertex position
v 0.066005 1.492495 -0.026312
...
vt 0.587890 0.748047               ← 2D UV texture coordinate
vt 0.593750 0.746094
...
f 4/1 2/2 1/3                      ← face: vertex_idx/uv_idx
f 8/4 6/5 5/6
...
```

### Counts

| Element | Count | OBJ prefix |
|---------|-------|------------|
| 3D vertices | **5023** | `v` |
| UV coordinates | **5118** | `vt` |
| Triangular faces | **9976** | `f` |

> **Key observation:** There are **5118 UV coords** but only **5023 vertices** — 95 extra UV entries. This is explained in Section 4 below.

### Face format: `f v_idx/vt_idx v_idx/vt_idx v_idx/vt_idx`

Each face line has 3 pairs separated by `/`:
- **Left of `/`** → index into `v` (3D vertex positions) → the **geometry** face
- **Right of `/`** → index into `vt` (UV coordinates) → the **texture** face

Example: `f 4/1 2/2 1/3` means:
- Triangle uses **geometry vertices** `[4, 2, 1]` (1-indexed in OBJ, 0-indexed after loading)
- Triangle uses **UV coordinates** `[1, 2, 3]`

These are two **independent indexing systems** for the same triangle.

## 3. `load_obj()` Return Values

```python
verts, faces, aux = load_obj(flame_template_mesh_path, load_textures=False)
```

PyTorch3D's `load_obj` parses the OBJ and returns three objects:

### 3.1 `verts` — Vertex Positions

- **Shape:** `(5023, 3)`
- **Type:** `torch.float32`
- **Content:** The `(x, y, z)` coordinates from all `v` lines.
- **Note:** These positions match `flame_model.v_template` from the `.pkl` — they represent the same neutral mesh.

### 3.2 `faces` — A NamedTuple with Two Index Arrays

`faces` is a `Faces` NamedTuple containing:

#### `faces.verts_idx` — Geometry Face Indices
- **Shape:** `(9976, 3)`
- **Type:** `torch.int64`
- **Content:** For each of the 9976 triangles, the 3 vertex indices (into `verts`). Parsed from the **left side** of each `/` in `f` lines.
- **Stored as:** `self.faces`

#### `faces.textures_idx` — UV/Texture Face Indices
- **Shape:** `(9976, 3)`
- **Type:** `torch.int64`
- **Content:** For each of the 9976 triangles, the 3 UV coordinate indices (into `aux.verts_uvs`). Parsed from the **right side** of each `/` in `f` lines.
- **Stored as:** `self.textures_idx`

#### `faces.normals_idx`
- **Shape:** `(9976, 3)` or empty
- **Content:** Normal indices — not used in FLAME since the OBJ has no `vn` lines.

### 3.3 `aux` — Auxiliary Data

`aux` is a `Properties` NamedTuple containing:

#### `aux.verts_uvs` — UV Coordinates
- **Shape:** `(5118, 2)`
- **Type:** `torch.float32`
- **Content:** The 2D `(u, v)` texture coordinates from all `vt` lines. Values are in `[0, 1]` representing position on the UV texture map.
- **Stored as:** `self.verts_uvs`

#### `aux.normals`
- Vertex normals — empty for FLAME OBJ (no `vn` lines).

#### `aux.material_colors`, `aux.texture_images`
- Material/texture info — not loaded (`load_textures=False`).

## 4. Why 5118 UV Coords ≠ 5023 Vertices — UV Seams Explained

### The Problem

In 3D space, a vertex has exactly **one** position. But in UV space, a vertex at a **seam** needs **multiple** UV coordinates — one for each side of the seam.

### Visual Intuition

Imagine unwrapping a head mesh into a flat 2D texture. You must **cut** the surface somewhere (e.g., along the back of the head, around the ears). At every cut edge, the same 3D vertex appears on **two different edges** of the UV layout, requiring two separate `(u, v)` values:

```
3D Space (1 vertex):          UV Space (2 UV coords for same vertex):

     * ← vertex #42               *  ← uv #42  (left island)
    /|\                           /|
   / | \                         / |
  /  |  \                      /  |
                               
                                  |
                                  * ← uv #5050 (right island)
                                   \
                                    \
```

### In Numbers

- **5023** unique 3D vertices
- **5118** UV coordinates = 5023 + **95 duplicates** at seam edges
- The **95 extra** UV entries are seam vertices that need different UV positions on each side of the cut

### How It Works in Code

The face definitions use **two separate index arrays** to handle this:

```
Face #0:  f 4/1 2/2 1/3
               │ │   │ │   │ │
               │ │   │ │   │ └─ UV index 3 (into 5118 UV coords)
               │ │   │ │   └─── Vertex index 1 (into 5023 vertices)
               │ │   │ └─────── UV index 2
               │ │   └───────── Vertex index 2
               │ └───────────── UV index 1
               └─────────────── Vertex index 4
```

Two different faces can reference the **same geometry vertex** but **different UV indices**:

```
f ... 42/42 ...     ← vertex 42, UV coord 42 (left side of seam)
f ... 42/5050 ...   ← vertex 42, UV coord 5050 (right side of seam)
```

## 5. The Assertion — Proving `.pkl` and `.obj` Share Topology

```python
assert (self.faces == torch.from_numpy(flame_model.f.astype('int64'))).all()
```

This critical assertion verifies that:

| `.pkl` field | `.obj` field | Must be identical |
|---|---|---|
| `flame_model.f` (shape `(9976, 3)`) | `faces.verts_idx` (shape `(9976, 3)`) | ✅ Same triangle connectivity |

Both contain the **geometry face indices** — which 3 vertices form each triangle. They **must** match because all the `.pkl` deformation data (blend shapes, skinning weights, etc.) is indexed by vertex, and the faces define how those vertices connect into a renderable mesh.

## 6. What Comes From Where — Complete Mapping

### From `.pkl` only (statistical model — for deformation)

| Code attribute | `.pkl` field | Shape | Purpose |
|---|---|---|---|
| `self.v_template` | `v_template` | `(5023, 3)` | Neutral mesh vertex positions |
| `self.shapedirs` | `shapedirs` | `(5023, 3, 400)` | Shape + expression PCA blend shape basis |
| `self.posedirs` | `posedirs` | `(36, 5023*3)` | Pose-corrective blend shapes |
| `self.J_regressor` | `J_regressor` | `(5, 5023)` | Joint position regressor |
| `self.parents` | `kintree_table` | `(5,)` | Kinematic tree parent indices |
| `self.lbs_weights` | `weights` | `(5023, 5)` | LBS skinning weights |

### From `.obj` only (UV mapping — for texturing)

| Code attribute | `.obj` source | Shape | Purpose |
|---|---|---|---|
| `self.verts_uvs` | `vt` lines → `aux.verts_uvs` | `(5118, 2)` | 2D UV texture coordinates |
| `self.textures_idx` | `f` right-of-`/` → `faces.textures_idx` | `(9976, 3)` | Per-face UV indices |
| `self.face_uvcoords` | Looked up from above | `(9976, 3, 3)` | Per-face UV coords (with padding) |

### From both (shared topology — must match)

| Code attribute | `.pkl` source | `.obj` source | Shape | Purpose |
|---|---|---|---|---|
| `self.faces` | `flame_model.f` | `faces.verts_idx` | `(9976, 3)` | Triangle face connectivity |

### Derived in code (computed at load time)

| Code attribute | Derived from | Shape | Purpose |
|---|---|---|---|
| `self.face_uvcoords` | `verts_uvs` indexed by `textures_idx` | `(9976, 3, 3)` | Per-face UV coords with homogeneous pad |
| per-vertex UVs (`vtx_uvs`) | Averaged from `face_uvcoords` per vertex | `(5023, 3)` | Mean UV per geometry vertex (for subdivision) |

## 7. How These Flow Into Rendering

```
                    ┌──────────────────────────────────────────────┐
                    │            .pkl (Statistical Model)          │
                    │                                              │
  shape β ────────► │  v_template + shapedirs·β + posedirs·θ      │
  expression ψ ──► │      → v_shaped                              │
  pose θ ─────────► │      → LBS(v_shaped, weights, joints)       │
  translation t ──► │      → v_final = v_deformed + t             │
                    │                                              │
                    └──────────────────┬───────────────────────────┘
                                       │ v_final (5023, 3)
                                       │
                    ┌──────────────────▼───────────────────────────┐
                    │        .obj (UV Mapping) + faces             │
                    │                                              │
                    │  faces.verts_idx → triangle mesh from v_final│
                    │  faces.textures_idx + verts_uvs → UV coords  │
                    │      → sample texture map for rendering      │
                    │                                              │
                    └──────────────────────────────────────────────┘
```

The `.pkl` produces **deformed 3D positions**. The `.obj` provides the **face connectivity** and **UV coordinates** needed to rasterize those positions into a textured image.

## 1. What Are `query_points`?

`query_points` are **canonical-space 3D positions on a subdivided FLAME mesh**, shaped `[B, N, 3]` where `N` is the number of upsampled vertices.

They are computed in `GS3DRenderer.get_query_points()` (`lam/models/rendering/gs_renderer.py:642`):

```python
def get_query_points(self, flame_data, device):
    with torch.no_grad():
        positions = self.flame_model.get_cano_verts(
            shape_params=flame_data["betas"]
        )  # [B, N, 3]
    return positions, flame_data
```

Which calls `FlameHeadSubdivided.get_cano_verts()` (`lam/models/rendering/flame_model/flame.py`):

```python
def get_cano_verts(self, shape_params):
    template_vertices = self.v_template_up.unsqueeze(0).expand(batch_size, -1, -1)
    v_shaped = template_vertices + blend_shapes(shape_params, self.shapedirs_up[:, :, :self.n_shape_params])
    return v_shaped
```

**In plain language:** The FLAME template mesh is subdivided (e.g., 2 times) to increase vertex density, then the identity-specific shape parameters (`betas`) are applied to deform the template into the subject's canonical face shape. These canonical vertices become the `query_points`.

---

## 2. Why Are They Called "Query Points"?

They serve as **spatial queries** into the transformer. Each query point is a 3D position on the face mesh, and the model uses it to "query" visual features from the input image to predict Gaussian Splatting attributes (color, opacity, scale, etc.) at that location.

This is analogous to how DETR uses object queries, but here the queries are **geometrically grounded** on a parametric face model.

---

## 3. The Full LAM Pipeline

LAM (Large Avatar Model) reconstructs an animatable 3D Gaussian Splatting head from a **single image**. The pipeline has 4 stages:

### Stage 1: Generate Query Points from FLAME

```
flame_params["betas"]  -->  FlameHeadSubdivided.get_cano_verts()  -->  query_points [B, N, 3]
```

- The FLAME parametric face model provides a structured 3D prior
- The base mesh (~5k vertices) is subdivided (e.g., 2x -> ~20k vertices) for finer detail
- Shape parameters personalize the template to the identity

### Stage 2: Encode Image Features

```
input_image [B, C, H, W]  -->  DINOv2 Encoder  -->  image_feats [B, L, D]
```

- A frozen DINOv2 vision transformer extracts semantic features from the input image
- These features encode appearance, texture, lighting, and geometry cues

### Stage 3: Cross-Attention Transformer

```
query_points  -->  PointEmbed (positional encoding)  -->  query_tokens [B, N, D]
query_tokens + image_feats  -->  TransformerDecoder  -->  latent_points [B, N, D]
```

- Each 3D query point is converted into a token via positional encoding (`sin/cos` embedding + MLP)
- The transformer uses **cross-attention** between query tokens and image features
- Each query token attends to image features to gather appearance information for its 3D location
- Output: a per-vertex latent feature vector

### Stage 4: Decode to 3D Gaussians and Render

```
latent_points  -->  GSLayer (linear heads)  -->  GaussianModel (xyz_offset, color, opacity, scale, rotation)
                                                          |
query_points + xyz_offset = canonical Gaussian positions  |
                                                          v
animation_forward(canonical_positions, expression, pose)  -->  posed Gaussians
                                                          |
                                                          v
                                            Gaussian Splatting Renderer  -->  rendered image
```

- The `GSLayer` decodes each latent vector into Gaussian Splatting attributes:
  - **xyz offset**: small displacement from the query point (restricted by `xyz_offset_max_step`)
  - **SH coefficients** (color): spherical harmonics for view-dependent appearance
  - **opacity**: transparency of each Gaussian
  - **scaling**: size of each Gaussian
  - **rotation**: orientation quaternion
- The canonical Gaussians are **animated** to the target pose via FLAME's linear blend skinning (LBS)
- The posed Gaussians are rasterized to produce the final image

## 5. Why This Design?

| Design Choice | Reason |
|---|---|
| **FLAME mesh as query points** | Provides strong geometric prior for face structure; no need to learn 3D layout from scratch |
| **Mesh subdivision** | Increases vertex density for finer detail (hair, wrinkles, lips) |
| **Canonical space** | Decouples identity/appearance from pose; enables animation by simply changing FLAME parameters |
| **Per-vertex Gaussian prediction** | Each mesh vertex anchors a 3D Gaussian, making the representation animatable via LBS |
| **Cross-attention with image features** | Allows each 3D point to gather relevant appearance info from the 2D image |
| **Small xyz offsets** | Lets Gaussians deviate slightly from the mesh surface to capture details like hair and accessories |

---

## 6. Key Difference: `e2e_flame` vs `flame` Query Points

The `latent_query_points_type` setting controls how query points are generated:

- **`e2e_flame`** (end-to-end): Query points are computed **dynamically** from per-sample `betas` via `get_query_points()`. The canonical mesh is personalized per identity. This is the mode used in the code path we're analyzing.

- **`flame`** (fixed): Query points are loaded from a **pre-saved .npy file** and shared across all samples. The mesh is a fixed template without identity-specific shape.

The `e2e_flame` approach is more expressive because the query points adapt to each person's face shape.
